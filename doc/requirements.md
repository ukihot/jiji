# 作品管理ツール「Jiji」要件定義 v0.3

**国産TVアニメーション制作のための Living Timeline**

---

# 1. 位置づけ

## 1.1 一文定義

> **絵コンテから完パケまで、1本のタイムラインが更新され続ける作品管理ツール。**
>
> そのタイムラインは、作品の現在形であり、制作の履歴であり、成果物への入口であり、監査証跡である。

Jijiは、制作工程を別々のタスクやファイルとして管理するのではなく、**作品そのものを一本の時間軸として管理する**。

絵コンテで描かれたカットは、アニマティクスになり、レイアウトになり、作画・3D・美術・撮影を経て、最終的な映像になる。

その過程で、

* 何が予定されていたか
* 何が提出されたか
* 何が採用されたか
* 何が変更されたか
* 誰が確認したか
* いつ完成したか

を、同じタイムライン上で追跡できる。

**Jijiでは、制作が進むほどタイムラインが完成作品に近づいていく。**

---

## 1.2 コアコンセプト

### Living Timeline

> **作品が完成するまで、タイムラインは一度も途切れない。**

```text
絵コンテ
    ↓
アニマティクス
    ↓
レイアウト
    ↓
作画 / 3D / 美術
    ↓
撮影
    ↓
仮編集
    ↓
音響
    ↓
カラー
    ↓
完パケ
```

工程が進んでも、作品を別の管理単位に分解しない。

**同じ時間軸が更新され続ける。**

### Cut Lineage（カット系譜）

> **同じカットは、工程を経るごとに姿を変えながら、一つの系譜として繋がっている。**

```text
Cut C-125
 ├─ Storyboard      （意図）
 ├─ Layout          （画面設計）
 ├─ Animation        （動き）
 ├─ BG               （背景）
 ├─ CG Render (EXR)  （光学的表現）
 ├─ Composite        （合成）
 └─ Final            （納品）
```

絵コンテはPNG、背景はPSD、CGレンダーはEXR、確認はMP4、納品はProRes——同じカットが、工程ごとに異なるファイル形式・異なる意味で存在する。Jijiはこれらを別々の成果物として管理しない。

絵コンテは映像になる前の意図であり、EXRは光学的表現であり、PSDは描画表現であり、MP4は確認表現であり、ProResは納品表現である。**形式は違っても、すべて同じカットの異なる表現形態（Representation）である。**

Living Timelineが「作品全体を時間軸として束ねる」のに対し、Cut Lineageは「1カットを表現形態の系譜として束ねる」。両者は直交する2つの軸であり、個々の成果物はこの2軸の交点に位置づけられる。

```text
        Living Timeline（横軸：時間・全カット）
              ───────────────────▶

Cut Lineage  Storyboard
（縦軸：       Layout
 1カットの      Animation
 表現形態）      ⋮
   │           Final
   ▼
```

---

## 1.3 Jijiが管理するもの

Jijiは「タスク」を中心に設計しない。

Jijiが中心に置くのは、

> **作品の時間軸**

である。

```text
                    ┌─ 絵コンテ
                    ├─ アニマティクス
                    ├─ レイアウト
                    ├─ 作画
作品の時間軸 ───────┼─ 3D
                    ├─ 美術
                    ├─ 撮影
                    ├─ 音響
                    └─ 完パケ
```

カット、素材、工程、レビュー、提出物、課題、アセットは、すべてこの時間軸に接続される。

したがってJijiにおける「進捗」とは、

> **何％終わったか**

ではない。

> **このタイムラインのどこまでが、どの品質で、どの時点まで完成しているか**

である。

---

## 1.4 四本柱

| 柱                   | 内容                          |
| ------------------- | --------------------------- |
| **Living Timeline** | 絵コンテから完パケまで、同一タイムラインを更新し続ける |
| **Cut Lineage**     | 同じカットの異なる表現形態（絵コンテ〜完パケ）を一つの系譜として統合する |
| **尺と映像の一体管理**       | コマ単位の尺管理、通し再生、予定尺と実尺の比較     |
| **監査可能な制作履歴**       | すべての変更・提出・確認・共有を追跡可能にする     |

セキュリティは独立した機能ではなく、**Living Timeline / Cut Lineageの履歴を壊さないための基盤**として扱う。

# 2. 設計原則

Jijiは以下の原則を守る。

### P-01　タイムラインが正規の作品表現である

一覧表、タスク表、カンバンを正規UIとしない。

作品はタイムラインとして存在する。

---

### P-02　進捗率を持たない

`37% 完了` のような抽象的な進捗率は保持しない。

進捗は、

* 最新イベント
* 最新提出物
* 合格版
* 現在の工程
* 停滞期間

から観測する。

---

### P-03　工程は状態ではなく履歴である

「LO済み」「作監済み」のような状態フラグを主データとして持たない。

工程を通過した事実はイベントとして記録する。

```text
Cut
 ├─ LO submitted
 ├─ 演出 reviewed
 ├─ 作監 returned
 ├─ 一原 submitted
 ├─ 作監 approved
 ├─ 二原 submitted
 └─ ...
```

現在状態はイベント履歴から導出する。

---

### P-04　過去は消さない

提出物、レビュー、イベントは上書きしない。

変更は常に新しいイベントとして記録する。

---

### P-05　原本を奪わない

Jijiは制作データの「保管庫」ではない。

NAS、S3互換ストレージ、ローカルファイルシステム等に存在する原本を参照する。

Jijiが保持するのは、

* メタデータ
* イベント
* 提出物への参照
* プロキシ
* ハッシュ

である。

---

### P-06　制作現場の入力を増やさない

Jijiに情報を登録すること自体が新しい仕事になってはならない。

> **記録に要する時間が作業時間の5%を超えるUIはバグである。**

---

# 3. 対象と非対象

## 対象ユーザー

| 役割         | 主な用途                    |
| ---------- | ----------------------- |
| 制作進行       | タイムライン全体の追跡、素材受け渡し、停滞確認 |
| 監督・演出      | 通し再生、確認、リテイク            |
| 作画監督・総作画監督 | 作画品質の確認                 |
| 撮影監督       | 撮影工程の確認                 |
| 美術監督       | 背景工程の確認                 |
| 色彩設計       | 色彩工程の確認                 |
| 原画・動画・仕上   | 素材受領、提出                 |
| 3D制作スタッフ   | アセット・カット素材の提出           |
| 外部制作会社     | 共有リンク経由で提出・確認           |

## 非対象

* 経理・総務
* 一般的なタスク管理
* ガントチャート
* 工数管理
* 人員配置
* 請求・支払い
* 給与・評価
* SNS・コミュニケーション基盤

Jijiは**制作管理システム**ではあるが、**会社業務全般の管理システムではない**。

# 4. ユビキタス言語

## 4.1 作品構造

| 階層 | 呼称  | 識別子       |
| -- | --- | --------- |
| 1  | 作品  | `title`   |
| 2  | 期   | `season`  |
| 3  | 話数  | `episode` |
| 4  | パート | `part`    |
| 5  | シーン | `scene`   |
| 6  | カット | `cut`     |

ただし、**シーンは管理上の階層ではない**。

シーンは制作中に変動するため、カットに付与される論理的なグルーピング情報として扱う。

作品の実体は、

```text
Episode（Timeline）
 └─ TimelineItem
      ├─ Cut          … MVPで実装する中心的な種別
      ├─ Audio        （将来）
      ├─ Transition   （将来）
      └─ Marker       （将来）
```

である。`Cut`は`TimelineItem`の一種として扱う。OP・ED・CM・提供・アイキャッチ、あるいは劇場版・配信版といったカットではないTimeline構成要素も、将来同じTimeline上の要素として自然に扱えるようにするための一般化であり、物理設計はdoc/design.md 4章に置く。MVPで実装するのはCutのみ（13章 Phase 1）。

---

## 4.2 カット

`Cut` はJijiにおける制作管理の最小単位。

カットは、

> **作品の時間軸上に存在する、意味を持った映像区間**

である。

カット番号は文字列とする。

```text
C-001
C-002
C-125A
C-125B
C-130
```

ソート順は独立した `sort_order` で管理する。

---

## 4.3 タイムライン

タイムラインは、話数単位で保持する。

```text
Episode 03

00:00                  12:00                 24:00
│                       │                       │
├─ OP ─┬─ A ───────────┼─ B ───────────┬─ ED ─┤
       │               │               │
       C01 C02 C03 ... C125 ... C240
```

横軸の正規単位は**整数のコマ数**。

基準フレームレートは24fps。

表示は、

```text
3+12
```

形式とする。

---

## 4.4 Representation（表現体）とCut Lineage

`Representation` は、あるCutが特定の工程段階において取る**表現形態**を指す。

| Representation | 典型的な形式 | 対応する工程（7章、目安） |
| --- | --- | --- |
| Storyboard（絵コンテ） | PNG / PDF | 絵コンテ |
| Animatic | MP4 | アニマティクス |
| Layout | PSD | LO |
| Animation | PSD / 連番PNG | 一原〜動画 |
| BG | PSD | 美術 |
| CG Render | EXR（マルチAOV） | 3D Rendering |
| Composite | AEP / PSD / EXR | 撮影 |
| Final | ProRes / MP4 | 完パケ |

同一Cutに属するRepresentationの集合を、時系列で束ねたものを **Cut Lineage（カット系譜）** と呼ぶ（1.2節）。

Representationは工程と1対1ではない。複数の工程ステップ（一原・演出・作監・二原・動画）が同じ「Animation」というRepresentationの中でVersionを重ねていくこともあれば、CG RenderのようにEXRのAOVレイヤーという内部構造を持つRepresentationもある。RepresentationとVersionの関係は6.1節・6.2節で定義する。

---

# 5. Living Timelineモデル

## 5.1 タイムラインは「一枚の作品」である

Jijiでは、絵コンテと完パケを別の成果物として扱わない。

同じタイムライン上に、作品の異なる時点を記録する。

```text
             現在
               ↓

Storyboard ────┐
Animatic ──────┤
Layout ────────┤
Animation ─────┤
Compositing ───┤
Final ─────────┘
```

各段階は「別作品」ではなく、**同じ作品の異なる時点**である。

この「段階」の並びは、タイムライン全体（すべてのカット）を通して観測したものである。同じ並びを**1つのCutに絞って**見たものがCut Lineage（1.2節・4.4節）であり、上図とCut Lineageの図は同じ軸を異なる粒度（全カット／単一カット）で見ている。

---

## 5.2 Timeline Snapshot

タイムラインは任意の時点で再現可能である。

```text
2026-01-01
  └─ 絵コンテ版

2026-01-15
  └─ アニマティクス版

2026-02-10
  └─ 仮編集版

2026-03-20
  └─ 完パケ版
```

これにより、

> 「この作品は、いつ、どう変化したか」

を再現できる。

---

## 5.3 タイムトラベル

過去時点のタイムラインを再構成し、通し再生できる。

```text
[2026/01/01] ───────●────────── [現在]
                      ↑
                   再生時点
```

これにより、

> 「絵コンテ段階ではどうだったか」
>
> 「仮編集段階で何が変わったか」
>
> 「いつこのカットが追加されたか」

を映像として確認できる。

---

# 6. ドメインモデル

## 中核エンティティ

| エンティティ       | 役割              |
| ------------ | --------------- |
| `Timeline`   | 作品の時間軸          |
| `TimelineItem` | タイムラインを構成する要素の総称（Cut/Audio/Transition/Marker等。4.1節） |
| `Cut`        | タイムラインを構成する映像区間（`TimelineItem`の一種。MVPで実装する中心的な種別） |
| `Representation` | Cutが工程を経て取る個々の表現形態（Storyboard/Layout/Animation/CG Render等）。Cut Lineageを構成する単位（4.4節） |
| `Asset`      | カット横断で利用される共有素材 |
| `CutAsset`   | カットとアセットの関係     |
| `Submission` | 特定のRepresentationに対する制作物の提出 |
| `Version`    | 提出物の不変な版（Representation配下で連番管理） |
| `Review`     | 確認・判断           |
| `Seal`       | 合格版の封印          |
| `Issue`      | 解決すべき課題         |
| `Event`      | 制作上発生した事実       |
| `ShareLink`  | 外部共有経路          |
| `Person`     | 人               |
| `Membership` | 人が作品にアクセスできる権限（役割・範囲・有効期限） |

---

## 6.1 Representation

`Representation` は、Cutが工程を経て取る個々の表現形態である。

```text
C-125
 ├─ Representation: Storyboard
 ├─ Representation: Layout
 ├─ Representation: Animation
 ├─ Representation: BG
 ├─ Representation: CG Render
 ├─ Representation: Composite
 └─ Representation: Final
```

1つのRepresentationは、複数のVersionを持つ（6.2節）。RepresentationはCutに従属し、Cutに属するRepresentationの集合がCut Lineage（4.4節）である。

EXRのように、1つのVersionが内部に複数レイヤー（AOV: beauty / diffuse / specular / normal 等）を持つ場合がある。JijiはこれをVersionのメタデータとして保持し、レイヤー単体を独立したRepresentationやVersionとしては扱わない（F-25）。

---

## 6.2 Version

同一Representation内で、提出物は上書きしない。

```text
C-125 / Animation
 ├─ Version 01
 ├─ Version 02
 ├─ Version 03
 └─ Version 04 ← 最新
```

ただし「最新版」と「採用版」は異なる。

```text
Latest Version
      ≠
Approved Version
```

これをJijiの重要な概念とする。

---

## 6.3 Seal

`Seal` は「その版を採用した」という事実を記録する。

```text
Version
   ↓
Hash
   ↓
Seal
   ↓
Approved
```

合格後に変更された場合、Jijiは変更を検知する。

ただし変更そのものを禁止しない。

> **Jijiは改竄を防止するのではなく、変更を隠せなくする。**

---

## 6.4 Issue

課題は `Open / Closed` の2状態のみ。

中間状態は持たない。

```text
Issue
  ├─ Open
  │    ├─ Event
  │    ├─ Event
  │    └─ Event
  │
  └─ Closed
```

Open時には閉栓権者を必須指定。

Closed時には理由を必須指定。

| 理由   | 意味     |
| ---- | ------ |
| 解決   | 対処した   |
| 不採用  | やらない   |
| 状況変化 | 不要になった |
| 再現なし | 未解明    |
| 再定義  | 別課題へ移管 |
| 失効   | 期限切れ   |

再オープンは既存Issueを書き換えず、新しいIssueとして起票する。

---

# 7. 工程モデル

工程は固定的なステータス列ではなく、**DAGとして扱う**。

```text
Asset
  モデリング
      ↓
  リグ / セットアップ
      ↓
  ルックデブ
      │
      ▼
3D
  3DLO
      ↓
  Animation
      ↓
  Lighting
      ↓
  Rendering
      │
      ├──────────────┐
      ▼              │
作画                 │
  LO                 │
   ↓                 │
  一原                │
   ↓                 │
  演出                │
   ↓                 │
  作監                │
   ↓                 │
  二原                │
   ↓                 │
  動画                │
   ↓                 │
  仕上                │
      │              │
      └──────┬───────┘
             ▼
            撮影
             ↑
             │
            BG
             │
             └──── 美術
```

JijiはこのDAGを**ユーザーが自由に設計するワークフローエンジンにはしない**。

国産TVアニメーションに必要な工程モデルを標準として持ち、必要最小限の拡張のみ許可する。

# 9. セキュリティと監査

セキュリティはJijiの主目的ではない。

**Living Timelineの信頼性を担保するための基盤**である。

### 原則

> **何が起きたかを、後から消せない。**

* 外部通信ゼロ
* エアギャップ動作可能
* イベントログ追記専用
* ハッシュチェーン
* 管理者によるログ削除不可
* 共有リンクは期限必須
* アカウントのアクセス権にも有効期限を設定できる（単話のみ参加するスタッフ・外部委託を常態として想定する）
* 作品単位の一括失効
* 全アクセス記録
* AI機能は完全分離・既定無効

生成AIを導入しない環境では、**Jijiのバイナリがネットワークに接続する理由そのものが存在しない**ことを保証する。

# 10. データ戦略

Jijiはストレージシステムではない。

```text
              Jiji
                │
       ┌────────┼────────┐
       ↓        ↓        ↓
      NAS      S3      Local
       │        │        │
       └────────┼────────┘
                ↓
        Metadata / Event
        Proxy / Hash
```

原本を移動・複製しない。「NAS / S3 / Local」は代表例であり、Google Drive・Dropboxのようなクラウドストレージも同じ位置づけの原本置き場として扱える（F-42, Should。design.md 9章）。

Jijiが管理するのは、

> **作品そのものではなく、作品がどこにあり、どう変化し、何が採用されたか**

である。

---

## 10.1 なぜ「なくてはならない」存在になるか

Jijiはファイルサービスを代替しない。だからこそ導入障壁がない。

```text
Jiji導入 = 既存ストレージの上に薄いレイヤーを足すだけ
        ≠ 既存ストレージの置き換え
```

しかし、Jijiの外には存在しない記録がある。

> **どの版が、いつ、誰によって、なぜ合格とされたか。**

原本ファイルはNAS / S3 / ローカルのどこにあってもよい。ファイルだけを見ても、それが合格版なのか、差し戻し中なのか、なぜ変更されたのかはわからない。

同様に、EXRファイル単体を見ても、それがどのCutのどの表現段階（Representation）に属するかはファイルシステム上には残らない。その系譜（Cut Lineage）を保持するのもJijiだけである。

その意味構造 — Representation / Version / Seal / Event / Issue — は、Jijiだけが保持する。

```text
ファイル本体      → 既存ストレージに残る（寄生先）
意味・合否・履歴   → Jijiだけが持つ（Jijiにしかない）
```

したがって、

* **導入時**：既存の運用・既存ストレージを壊さないので抵抗が少ない
* **定着後**：合否と履歴の唯一の記録がJijiにあるため、離脱コストが高い

**Jijiは「ファイルを管理する」ことでは主導権を握らない。「ファイルの意味を管理する」ことで、後から外せない存在になる。**

これは機能の多寡でKitsuと競争しないこと（14章）とも整合する。競争するのは機能ではなく、**制作の意味構造をどちらが記録し続けているか**という一点である。

# 11. 実行環境要件

技術選定・アーキテクチャ・プロキシ生成の具体的な戦略は設計事項であり、**doc/design.md**に分離する。

要件定義が定めるのは、実装がどの技術を選んでも満たすべき制約のみ。

* シングルバイナリ、または`docker run`一発で起動できること。外部DBに依存しないこと
* メディア処理（プロキシ生成・結合）はローカルで完結すること。外部サービスへのアップロードを要求しないこと
* プロキシ生成は変更差分のみとし、バックグラウンドで実行されること
* 通し再生時のシークは即応すること

# 12. UI

Jijiの主画面は、**Timeline EditorではなくTimeline Viewer**である。

ユーザーが最初に見るものは、

> **現在の作品**

である。

作品全体を俯瞰するTimeline Viewerに対して、1カットを掘り下げる**Cut Evolution Viewer**を副画面として持つ。Cut Lineage（1.2節・4.4節）をカット単位で展開し、Representationを並べて比較・切替できる（F-22, F-27）。ただし主従は変わらない——Cut Evolution Viewerは常にTimeline Viewer上のカットから遷移する詳細ビューであり、独立した入口を持たない（P-01：タイムラインが正規の作品表現である）。

画面レイアウトの具体案（ワイヤーフレーム）はdoc/design.mdに置く。要件として定めるのは、以下の性質のみ。

UIの8割は作品。

メニューや管理画面は作品の裏側に置く。

色は装飾ではなく、**異常・課題・状態の表現だけに使用する**。

# 13. 開発フェーズ

ここも少し変える。

Jijiの最大のリスクは「セキュリティ」ではない。

**Living Timelineが本当に制作現場で成立するか**である。

| Phase | 内容                            | Go / No-Go                     |
| ----- | ----------------------------- | ------------------------------ |
| **0** | Kitsu検証＋実際のカット表収集             | 国産TVアニメの実データモデルが定義できる          |
| **1** | Timeline＋Cut＋尺モデル             | 実カット表からタイムラインを再構成できる           |
| **2** | Version＋Proxy＋通し再生            | **絵コンテから完成映像まで同一Timelineで扱える** |
| **3** | Submission＋Review＋Seal        | 制作物の提出と合格がTimelineに接続される       |
| **4** | 外部共有                          | アカウントレスで外注工程を接続できる             |
| **5** | Event Log＋Audit               | 制作履歴を完全に再構成できる                 |
| **6** | Timeline Snapshot＋Time Travel | 過去の作品状態を映像として再現できる             |
| **7** | Asset Graph                   | カット横断の依存関係を追跡できる               |

**Phase 2がJijiの本当の山場。**

ここで、

> 絵コンテ
> ↓
> アニマティクス
> ↓
> 作画・3D
> ↓
> 撮影
> ↓
> 完パケ

が**一本のTimelineとして本当に繋がる**なら、Jijiは成立する。

これを1カットで見れば、Representationが途切れず繋がり、Cut Lineage（1.2節）が成立している状態と同義である。

# 15. Jijiの本質

Jijiは、**「アニメ制作の進捗管理ツール」ではない。****「制作物を管理するDAMでもない。****「タスク管理ツール」でもない。**Jijiが管理するのは、

> **作品が、複数の表現形態を経由しながら完成していく時間そのもの**

である。

だから、

```text
絵コンテ
   ↓
アニマティクス
   ↓
制作
   ↓
編集
   ↓
完パケ
```

は、Jijiの中では別々の工程ではない。

**一本の作品が、時間とともに変化していく過程である。**

その結果として、

> **現在のタイムライン = 現在の作品**
>
> **過去のタイムライン = 過去の作品**
>
> **イベント履歴 = 作品が変化した理由**
>
> **成果物 = タイムライン上の各時点に存在する実体**
>
> **Cut Lineage = 1カットが辿ってきた表現形態の道のり**

となる。

そして最終的にJijiは、

> **「この作品は、どうやって今の姿になったのか？」**

という問いに、タイムラインそのものを使って答えられる。

これがJijiの唯一の中核価値であり、他の機能はすべてここから派生する。
